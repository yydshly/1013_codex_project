## 先把库、Jev 与我们的扩展分清楚

**Hermes Jev Skills 是接入与编排工具库；Jev 是它调用的云端判断模型；我们整理的能力路由和个人标准，是在这一分工基础上提出的使用方案。** 三者有关系，但不是同一个东西。

| 读者的问题 | 直接理解 |
| --- | --- |
| 这个库能做什么？ | 给 Agent 接入模型路由、技能选择、检索结果筛选、证据充分性判断、消息分类和合法候选动作选择等有限决策。 |
| Jev 在哪里？ | 在某个工作流的判断环节，接受必要状态与定义好的问题，返回有限答案；应用代码再决定下一步。 |
| Jev 负责什么？ | 理解给定状态并按问题选择、评分或判断是否满足条件。多模型路由中，它判断任务需求，不直接证明执行模型的能力。 |
| 谁制定标准？ | 库作者提供默认问题与策略。接入自己的业务时，由我们定义、复用或修改标准、候选、约束、模型池和验收要求，再用数据修订。 |
| 谁真正完成任务？ | 主模型、执行模型、检索器、应用代码与工具。Jev 不承担最终正文、代码修改、地图同步或检索事实的生成。 |
| 我应该学什么？ | 找出反复出现的判断，拆成清晰问题；固定分支用规则，语义判断再比较 Jev / 小模型；用成果验收决定是否保留。 |

比如“让地图、音频和镜头共用暂停恢复进度”：我们定义“改变部件间行为依赖”的标准；判断器识别该需求；本地策略暂选 B；执行模型修改代码；运行和交互检查验证进度是否一致。**Jev 起作用的是识别需求这一环，后续动作需要其他组件完成。** 这只是个人方案的教学示例，未真实调用模型。

## 库的能力与边界

| 能力 | 给判断器的材料 / 问题 | 后续由谁做 |

| 记忆与上下文筛选 | 候选片段 / 对话轮次；相关性、保留价值等 | 本地代码保留或组织上下文；主模型阅读或写交接摘要 |

## 我们形成的理解

值得借鉴的是按任务需要的能力划分工作，把有限判断与生成、执行分开。Jev 是 TypeSafe 的决策模型；本仓库主要提供接入代码、技能与策略，没有 Jev 的权重和训练实现。多模型路由是其中一种用途，还可以做技能选择、证据充分性判断、候选动作选择等。

在默认路由中，Jev 判断难度、类型和出错代价；本地代码结合模型池、阈值、上下文和图像要求选择具体模型。任务被判断为简单，不等于某个便宜模型一定能做好；执行模型能力和路由映射要靠自己的任务实测。

判断器可以换成本地规则或其他小模型。替代需要适配接口、输出校验与回退，不能把普通模型的自报置信度直接当成可靠概率。是否值得使用，取决于相对现有流程的完成质量、总成本、延迟、返工与维护收益。

## 上游实际架构：Jev 位于哪里

以 Hermes 的模型路由为例，固定版本的职责链是：

```text
用户请求 → Hermes 路由扩展点
         → jevkit 构造脱敏状态、难度 / 类型 / 风险问题
         → TypeSafe Jev 云 API 返回结构化判断
         → 客户端校验 + 本地阈值、约束与模型池
         → Hermes 切换可用模型 → 主模型与工具执行
```

Jev 提供决策依据，调用方代码负责把依据落实成可执行选择。用户固定模型、上下文、图像能力、候选可用性和供应商连接等约束可能覆盖判断；接口失败也必须有本地回退。Jev 无法看到没有提交给它的项目事实，也不会自行替你生成完整模型能力评测。

原库默认路由已经定义了标准，我们可以先使用，再用自己的数据调整；并不是每次请求都由用户临时写规则。厂商文档称 Jev 针对有限决策与概率校准训练；这是厂商对模型原理的说明，无法从接入库独立审计训练细节。

## 我们扩展的架构：先规则，再按需要判断

```text
任务 + 必要背景 + 验收要求
    → 本地硬约束与固定任务规则
    → 有语义歧义时：Jev / 小模型 + 判断标准
    → 本地策略与模型池 → 执行模型 + 工具
    → 产出验收 → 记录失败、修订标准
```

这是我们的设计建议，加入了规则优先和执行验收，不是上游路由的逐项复刻。具体场景应分别写清三层：

| 层次 | 回答的问题 | 导览联动例子 |
| --- | --- | --- |
| 场景架构 | 谁观察、谁判断、谁执行、谁验收？ | 输入真实需求；判断依赖；策略选模型；模型改代码；浏览器检验 |
| 判断标准 | 如何从材料识别需求？ | 是否改变音频、地图、镜头之间的共享进度和暂停行为 |
| 路由策略 | 判断之后采取什么行动？ | 有依赖暂用 B；仅改已审核字幕试 A；缺背景先补信息 |

改变“识别到依赖后选 B”的策略，不一定要更换判断器；更换 Jev，也不必重新设计整个场景。真正应验证的是各层组合后能否稳定交付。

### 默认实现的源码证据

默认实现见固定版本 [jevkit/route.py](https://github.com/kerpopule/hermes-jev-skills/blob/31f476cac49713b6bf88c00d42382542e1c36965/jevkit/route.py)：

- `DIFFICULTY` 定义机械、常规、较复杂、专家四级任务。
- `questions()` 同时询问难度、工作类型和出错代价，`decide()` 在本地组合回答与约束。
- 默认当前请求脱敏后上限约 2,500 字符，通常保留开头和结尾；并非完整历史与所有文件。只提供“继续完善”会缺乏必要背景。
- 默认最低置信度 0.6；降到 simple 要求 P(机械任务) ≥ 0.7 且置信度 ≥ 0.85；P(较难两级) ≥ 0.6 可进入 hard。风险等约束还能改变结果。它们是源码默认值，不是适合个人业务的已验证阈值。
- 用户固定模型优先；一般低置信度或接口故障保持当前模型，风险等规则另行处理。Hermes 插件可换模型但不自动切换供应商连接；Codex 的技能/CLI 不等于相同的自动路由中间件。

问题类型和返回校验见 [jevkit/client.py](https://github.com/kerpopule/hermes-jev-skills/blob/31f476cac49713b6bf88c00d42382542e1c36965/jevkit/client.py)。TypeSafe [介绍](https://docs.typesafe.ai/introduction)与[置信度说明](https://docs.typesafe.ai/confidence)解释了 Choice、Score、Noul。Choice / Score 的 confidence 是答案分布的集中程度；Noul 返回“是”的概率，没有另一个独立 confidence。它们不等于下游任务成功率。

## 标准如何制定

先选两个执行模型：A 为便宜候选，B 为较强候选。这些称呼不代表实测能力。先定义“完成”的验收标准，再提出路由假设。

| 任务 | 验收标准 | 初始假设 |
| --- | --- | --- |
| 已有字幕压缩 | 字数满足要求；保留事实、数字、专名；不补新结论 | 可以试 A |
| GitHub 项目研究 | 重要结论能指回源码；区分上游、本地扩展和未验证事项 | 已有结论整理可试 A；新分析暂用 B |
| 新疆导览联动修改 | 音频、地图、镜头进度一致；暂停、自由控制和返回正常 | 多部件联动暂用 B |

将抽象难度改成可复查的问题：仅改表达吗？需要跨材料综合推理吗？有部件间的共享状态或行为依赖吗？背景足够吗？错误能否低成本修复？“改三个按钮文字”不自动意味着联动，“地图和音频暂停恢复一致”则有真实依赖。

初始策略：背景不足先补信息；综合推理、相互依赖或较高风险暂用 B；明确的表达整理尝试 A；不确定时保持事先约定的默认模型。固定流程和硬字段优先规则，语义歧义再比较 Jev / 小模型。上述策略是待验证方案，不是默认路由的精确复刻。

### 七步把标准设置成可执行方案

1. **限定场景和目标。** 先做“已核实材料的表达整理”，目标是在事先约定的质量容限内降低每个通过任务的总成本。
2. **先写验收要求。** 字数、数字、专名、事实和格式怎么检查；人为评阅怎么判定，失败怎样记录。
3. **描述真实输入。** 保存材料是否齐全、允许修改的范围、已知约束和工具；不要让判断器凭一句“继续完善”猜整个项目。
4. **拆成能复查的问题。** 只改表达吗？要形成新结论吗？有行为依赖吗？错了是否难修？为“否”“未知”补上反例。
5. **写出动作和兜底。** 每种答案如何映射模型；图像、上下文、用户固定选择等硬约束放代码里；格式错误、缺信息和低把握分别怎么处理。
6. **配对执行形成依据。** 用开发集观察 A / B 实际能力，修改问题和模型映射；概率阈值单独检验，普通小模型自报数字不视为已校准。
7. **冻结版本再试运行。** 独立测试集比较四条基线；先影子记录，再小范围切换，按失败反馈修订并保留版本。

标准不是“复杂就贵”的口号，而是可复核的任务属性、可执行的映射、可检查的成果要求。判断器可以按标准应用语义判断，标准本身仍需要我们设计和维护。

## 如何验证标准与价值

1. 收集自己的任务，冻结输入、材料、工具、版本和验收标准。
2. A、B 分别完成同一任务；关键或不稳定案例重复执行，隐藏模型名称评阅。
3. 单独记录判断标准是否被正确应用、执行结果是否通过。
4. 开发集修改标准与阈值，测试集独立保留；兼顾真实任务分布与高代价边界案例。
5. 比较固定默认模型、规则、规则 + Jev、规则 + 小模型。
6. 影子模式只记录建议；离线评测后再小范围切换，持续记录失败、升级与人工返工。

| A / B | 含义 |
| --- | --- |
| 都通过 | 比较完整成本与延迟 |
| A 不通过、B 通过 | 需要避免误降级到 A |
| A 通过、B 不通过 | B 未必适合，需要调整模型映射 |
| 都不通过 | 检查材料、工具、验收与流程；升级不一定解决 |

Jev 正确应用标准而 A 做不好，是标准或模型映射问题；标准要求 B 而 Jev 漏掉联动，是输入、问题或判断器问题。总费用包括判断、全部执行调用、重试、升级和缓存变化；另记人工返工和维护工时。每个通过任务的成本 = 总费用 / 最终通过任务数。误降级率重点观察 A 不通过、B 通过的任务中，路由选择 A 的比例。

[上游 replay](https://github.com/kerpopule/hermes-jev-skills/blob/31f476cac49713b6bf88c00d42382542e1c36965/docs/measuring-a-router.md)只调用 Jev，不执行被选模型；可观察分布和估算成本，不能证明最终质量。几十条案例可以发现问题，不能证明罕见错误已经受控。质量损失容限、延迟预算应在看结果前确定。

## 对个人项目的价值

- Infinite Bookshelf：明确的目录、标题、章节阶段可直接配模型。表达整理可试 A，目录覆盖和全书一致性单独验收。
- 新疆导览 / 海底世界：批准的演示顺序用规则执行；新联动需求可做语义路由。播放、同步、帧更新等由场景代码负责。
- RAG：可判断当前证据是否覆盖问题；必须提供证据与覆盖标准，缺失证据需要继续检索。
- Leak Check：格式、精确匹配、既定关联适合规则。说明生成受已验证的脱敏结果约束，不能凭模型推断身份。

第一条可验证假设建议是：已有材料的表达整理，能否由 A 稳定完成。先做窄范围比较，再扩展。固定配置已足够，或路由开销大于节省时，保留规则方案。

对你更直接的意义是，把已有的源码研究、阶段拆解和网页验收经验变成可重复的判断标准。你现在已有“阶段、材料、约束、结果”的记录基础，可以先用规则建立对照，再研究哪些语义判断值得委托。有限判断也不意味着机械规则永远足够：例如“现有证据是否真的覆盖问题”有有限答案，但需要理解材料。

## 什么时候用规则，什么时候比较 Jev / 小模型

| 条件 | 建议起点 | 为什么 |
| --- | --- | --- |
| 入口已经标明字幕整理、章节阶段，或有长度、图像、上下文字段 | 本地规则 / 固定配置 | 信息明确，可直接执行，额外判断未必改变选择 |
| 自由文本反复出现，需要区分改表达、新推理和联动需求 | 规则兜底，再比较 Jev / 小模型 | 有语义判断需求；是否值得取决于误判、延迟和总费用 |
| 背景或材料缺失 | 补信息、检索或人工确认 | 换更强判断器不能得到未提供的事实 |
| 任务偶发，执行费用低，固定模型已满足要求 | 保留现有流程 | 增加集成与维护可能没有足够回报 |
| 必须每帧同步、精确计算或固定顺序执行 | 应用代码与规则 | 状态更新和执行约束应明确落地 |
| 没有验收办法、没有合法候选或失败没有兜底 | 先完善场景设计 | 暂时无法评判判断器是否带来价值 |

替换 Jev 时，保留状态、问题和本地策略，为普通小模型增加结构化输出适配、合法值校验和明确回退。不要把一段自由回答直接当可执行动作，也不要伪造 confidence 让它通过原接口。保留默认模型作基线；候选模型具体选型还需要当时价格、版本、能力和真实任务评测，本次没有证据给出胜出者。

## 可扩展场景的共同基础

扩展的基础不是“再找一个小模型”，而是这六个条件：**状态可观察、选项有限且合法、标准明确、动作可以落实、失败可以回退、结果可以验收。** 判断不会改变动作的维度可以删掉；只是换了行业名称，不代表已经有新的可靠方案。

| 可扩展方向 | 提供的状态与有限问题 | 执行与验收 |
| --- | --- | --- |
| RAG 证据充分性 | 问题、实际段落、覆盖清单；足够 / 不足 / 未知 | 不足继续检索；检查最终答案逐项证据覆盖 |
| 技能选择 | 当前任务、可用技能及用途；某技能 / 无需技能 | 加载技能；验收它是否实际帮助完成任务 |
| 流程重试与升级 | 检查失败、尝试次数与可选动作；重试 / 升级 / 补信息 / 结束 | 工作流执行并限制次数；记录最终通过与完整费用 |
| 交付前检查 | 草稿、核实材料、验收要求；通过 / 缺项 / 未知 | 确定性检查先做；语义缺项返工；仍需最终验收。这是扩展设想，不宣称库已提供完整交付门禁 |
| 消息与任务分流 | 消息、分类定义与可用责任人类别；队列 / 人工 / 未知 | 工作流分派；检查漏分、错分和处理时效 |
| 有限方案选择 | 预先批准的布局、脚本或动作及约束；选择一个 / 暂停 | 渲染器或工具执行；检查兼容性、结果与失败回退 |

对自动路由、证据判断、动作选择分别评测；在一个场景成功不能直接推出在其他场景也有效。允许列表限定的是能做哪些动作，不保证所选动作一定正确。
