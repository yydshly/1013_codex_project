一句话理解

这个库帮助你搭建自己的 VPN，并管理设备接入。它用脚本完成部署；WireGuard 负责 UDP 加密 IP 隧道，Linux 网络栈负责路由、转发和 NAT。

能力
自动搭建 WireGuard VPN，生成配置，添加与撤销设备。
原理
原始 IP 包认证加密 → 外层 UDP 封装 → 对端解封装 → 系统转发。
部署
准备可达 Linux 主机 → 运行安装器 → 设备导入配置 → 验证握手与业务。
价值
掌握出口和设备授权，减少手配；承担主机费用、系统维护和排错。
场景
个人集中出口、多设备接入；内网访问和网段分流需要额外网络配置。
扩展
访问策略、配置分发、Web 管理、监控和多网关；均需后续实现与验证。

能力是什么

自动部署 WireGuard，生成并管理每台设备的接入配置。

原理是什么

身份关系

客户端保存 自己的私钥 + 服务器公钥。服务器保存 自己的私钥 + 各客户端公钥。脚本另为每台设备生成一份共享密钥 PSK。

配置把身份、内部地址与外部位置关联起来。

长久身份密钥用于握手，会话收发密钥由握手派生。客户端应用与协议实现来自 WireGuard 的现有发行渠道。

字段客户端服务端
PrivateKey / PublicKey自己的私钥、服务器公钥。自己的私钥、每个客户端的公钥。
Address例如 10.7.0.2，赋给本机虚拟接口。默认 10.7.0.1，赋给 wg0。
Endpoint / ListenPortEndpoint 指向服务器可达地址和 UDP 端口。ListenPort 默认 51820；从认证包学习客户端当前外部位置。
AllowedIPs默认 0.0.0.0/0、::/0；配合平台路由把流量交给服务器 peer。给该 peer 绑定一个内部 /32 地址，双栈时加 /128；检查来包内部源 IP。
PresharedKey与该服务器 peer 共享的 PSK。与该客户端共享同一 PSK，混入握手派生。
DNS / Keepalive配置解析器；脚本设置 PersistentKeepalive = 25 秒。生成客户端字段；保活帮助维持 NAT 映射，可达性仍依赖实际网络。
配置交付也是授权过程。

脚本在服务端生成客户端私钥，并保存导出的配置；二维码同样包含接入凭据。每台设备使用独立配置，才能单独撤销。目标网站通常无需安装 WireGuard。

05 / DEPLOYMENT

部署先建立配置关系。

准备一台服务器；脚本完成系统配置，再把接入材料交给设备。

服务器

受支持的 Linux、root 权限及适用内核。本版本安装器拒绝容器；协议本身的容器能力需另行理解。

可达网络

客户端能够访问服务器 UDP 端口。公网地址、云安全组、上游 NAT 映射由实际部署环境决定。

设备

安装对应平台 WireGuard 应用或工具，导入配置；需要保管自己的接入凭据。

  1. 01

    检查并安装环境

    检查系统、内核和管理员权限，安装 WireGuard 与辅助工具。

  2. 02

    生成服务端配置

    生成服务器密钥，写入内部地址与 UDP 监听端口。

  3. 03

    开启转发，配置出口

    设置 IP 转发、NAT 与防火墙，让服务器能够转发客户端流量。

  4. 04

    登记设备，输出配置

    生成客户端密钥与内部 IP，输出配置文件和二维码。

  5. 05

    启动服务，设备接入

    启动 wg0 并设置开机启动；设备导入配置后建立隧道。

脚本完成操作后退出。

持续处理流量的是 WireGuard 和系统网络栈。云安全组、上游防火墙或 NAT 端口转发，需要在对应环境中配置。

后续添加设备时，脚本更新配置并将 peer 加到运行中的接口；撤销时移除运行状态中的 peer、持久配置及导出文件。公开实现采用局部更新，实际连接影响仍待测试。公网 IP 检测只帮助确定地址，不会创建上游端口映射。

07 / TUNNELING & FORWARDING

封装、解封装、转发：理解隧道本质。

我们的理解可以表述为：原始 IP 包经过认证加密，被包装在另一套外层 IP / UDP 协议里传输；对端验证、解封装，再交给系统继续处理。

从“包装目标协议”进一步精确到

包装整个内部 IP 包。TCP、UDP、TLS 和业务内容已经在这个 IP 包里面。外层目的地址指向 VPN 服务器；内部目的地址仍指向原来的目标服务。

“中转解析”分成三个层次。

每一层读取的字段和承担的责任不同。能处理隧道包，并不意味着网关已读懂或解密业务内容。

处理层次由谁执行实际发生的事
隧道处理两端 WireGuard读取 WG 消息，验证身份与完整性、防重放、解密，检查该 peer 的内部源 IP。
网络转发服务端 Linux 网络栈查看内部 IP 目标，应用路由与防火墙；出口 NAT 可改写源 IP / 端口，并维护返回映射。
业务处理客户端应用与目标服务处理 TLS、HTTP、SSH、DNS 等应用协议；正常 HTTPS 情形中，VPN 网关不持有网站 TLS 会话密钥。
隧道通信关系

客户端 WireGuard ↔ 服务端 WireGuard

对端由配置公钥标识，外部 endpoint 用于 UDP 寻址，握手派生的会话密钥保护内部 IP 包。

业务通信关系

客户端应用 ↔ 目标网站 / 服务

内部 TCP 继续维持自身连接、排序和重传；服务器作为网关，通常不终止内部 TCP 或 TLS 连接。

与 HTTP / SOCKS 代理、二层网络和自动中继怎样区分？
方式主要处理对象对这份研究的意义
WireGuard IP 隧道操作系统送入虚拟接口的 IP 包。经路由选中的应用无需逐个理解 WG 协议；是否走 VPN 由路由与平台配置决定。
HTTP / SOCKS 代理按代理协议接收请求或转接应用连接。常需要应用代理设置或转接层；代理可能终止传输连接，HTTPS 是否被终止取决于具体模式。
二层桥接以太网帧与二层网络行为。WG 是三层 IP 隧道，安装成功不会自动形成一个支持以太网广播发现的局域网。
自动协调与中继平台设备发现、网络穿透协调、路径选择等。本安装器提供集中网关配置，未提供相应协调、中继或自动网状组网服务。

隧道、peer 和路由依据：官方概念说明、技术白皮书。业务连接与 NAT 的说明是据封装层次所作的工程解释，本次未抓包验证。

08 / PROTOCOL & CRYPTOGRAPHY

外层 UDP，内层仍是你的业务。

传输协议和业务协议处在不同层。隧道同时负责加密与认证。

查看一个封装示例
外层 · 公网传输
IPUDPWireGuard
会话密钥保护的内部 IP 包
IPTCPTLS / HTTPS 数据

以使用 TCP 的 HTTPS 请求为例：内部 TCP 负责自身的排序与重传，外层 WireGuard 始终通过 UDP 发送。

传输

UDP 是隧道的外层协议

握手与数据消息都走 UDP，默认端口 51820。这个安装器没有提供 TCP 自动回退。

封装

传输的是三层 IP 包

可以承载内部 TCP、UDP 等 IP 流量；应用仍使用自己的协议。

边界

VPN 与 HTTPS 可以叠加

服务器解开 WireGuard 封装时，内部 HTTPS 的 TLS 加密仍然存在。

身份密钥与会话密钥，各做一件事。

配置中的身份密钥用于认证；握手派生的会话密钥用于业务数据保护。

机制使用的设计实际作用
认证与协商Noise 握手 · Curve25519验证配置中的对端身份，协商密钥材料。
数据加密ChaCha20-Poly1305保护内部 IP 包内容，并检测篡改。
额外共享秘密每客户端一份 PSK脚本生成额外共享密钥，混入握手过程。
防重放与更新时间戳 · 计数器 · 协议定时器抵御旧包重放，轮换会话密钥，提供前向保密。

握手采用 Noise IK 系列设计，密钥派生使用 BLAKE2s / HKDF。稳定公钥标识设备，会话密钥负责实际数据加密；身份公钥不直接逐包加密业务。已认证数据可更新对端 endpoint，帮助适应网络位置变化；保活帮助维持 NAT 状态，但不会让不可达的服务器自动变得可达。

谁能看到哪一层？

观察位置可观察内容加密边界
设备到服务器的链路外部 IP、UDP 端口、包长和时序等。内部 IP 包在 WG 认证加密范围内；这些外部元数据仍可观察。
VPN 服务器解封装后的内部 IP、传输层字段，以及未做应用加密的内容。普通 DNS 等明文业务可能被读取；正常 HTTPS 内容仍由 TLS 保护。
服务器到目标的链路业务流量的网络字段；明文内容取决于业务协议。离开 VPN 服务器后已无这条 WG 隧道保护，HTTPS / SSH 等应用加密继续存在。
目标网站或服务应用请求、登录身份等；默认出口 NAT 场景下通常看到服务器出口 IP。更换出口 IP 不会消除账号、Cookie 或设备指纹等识别方式。

密码学与 UDP 传输依据：官方协议。可见范围按默认出口拓扑及封装层次说明；未实测 DNS 泄漏、平台断线阻断或流量识别。

09 / USE CASES

场景决定路由，也决定额外工作。

以下是基于源码能力和网络结构推导的用途，不代表已完成实际部署。先确定需要“统一出口”还是“只访问某个网段”。

01默认配置覆盖

手机与电脑通过自己的服务器上网

客户端默认全流量配置，服务器解密后转发和 NAT。适合希望掌握自己的出口、给多台设备分别授权的人。

需要：可达的 UDP 服务、服务器出口带宽与流量预算；确认 DNS、IPv6 和本地网络访问行为。
02默认隧道可用

在不可信网络上，把部分信任转移到自有服务器

设备到服务器这一段由 WG 保护，降低沿途读取内部流量的机会。服务器与其后续网络仍是需要考虑的信任边界。

条件：路由实际经过 VPN；保持 HTTPS 等应用加密；断线阻断和 DNS 泄漏行为需按平台验证。
03需补充网络配置

远程访问家庭或办公室内网服务

服务器部署在能到达 NAS、开发机或内网应用的位置。客户端通过隧道访问这些内部地址。

需要：内网路由、返回路径或合适 NAT、访问防火墙、网段冲突处理；家庭服务器可能还需公网可达或端口映射。
04需修改两端配置

只让指定网段走 VPN，其他流量走本地

将客户端的 AllowedIPs 与系统路由改为目标网段，实现分流，减少无关流量绕行服务器。

需要：确定目标 IP 网段、返回路由和 DNS 策略；按域名或应用分流不能仅靠一个静态 CIDR 列表完成。
05可作为基础组件

个人实验室与小团队的密钥接入

独立配置身份方便添加和撤销。也可以进一步研究 peer 对 peer 或站点之间的三层路由。

需要：团队访问策略、设备隔离、分发与密钥生命周期管理；站点互联和自动 mesh 不是此脚本的开箱功能。
06当前研究用途

学习 Linux 网络、抓包和部署自动化

把配置文件、接口、握手、封装和 NAT 对应起来。比较外层 UDP 与内层 TCP / UDP，再验证添加和撤销。

能力边界：需要额外系统的部分。

以下为固定版本公开实现中未提供的完整能力；底层可扩展并不等于安装器已经实现。

账号与管理平台

未提供 Web 面板、管理 HTTP API、用户名密码、SSO / MFA、自助注册及自动配置分发。

网络协调与策略

未提供自动打洞协调、中继平台、mesh 管理、应用级 ACL 或逐设备隔离策略。

运营与连续性

未提供完整的额度计费、集中审计、容量管理、自动故障切换与密钥生命周期平台。

传输和效果保证

无 TCP 回退或混淆；更换端口仍是 UDP。速度、匿名性、DNS 防泄漏与断线阻断均不能由安装成功推定。

性能由设备、网关 CPU、带宽、路径和丢包共同决定。增加封装会增加包大小，绕行网关也可能增加延迟；遇到特定网站可用但大包卡住时，还应检查 MTU。网络参数调整和 BBR 设置不构成全链路加速保证。

它直接提供哪些能力？+

自动部署、配置生成、二维码导入材料、设备添加与撤销，以及服务端网络设置。默认是设备通过服务器上网的集中网关结构。

哪些需要我们另外设计？+

仅指定网段走 VPN、内网返回路由、客户端隔离、按应用授权，以及企业登录、审计与自助配置分发。公钥与内部 IP 的绑定不等于完整的访问权限系统。

默认 253 个客户端，意味着什么？+

脚本默认地址池可配置 253 个客户端。这是地址分配上限，不是经过测试的并发能力或性能承诺。

改成 443 端口，就变成 HTTPS 了吗？+

仍然是 WireGuard 的 UDP/443。端口变化不改变协议；安装器没有提供 TCP 回退、传输混淆或自动中继服务。

二维码与配置文件包含什么？+

包含该设备的私钥、服务器公钥、共享密钥与连接参数，是完整的接入凭据。脚本在服务端生成并导出这些材料，由操作者交给设备。

加密覆盖到哪里？速度有保证吗？+

VPN 加密覆盖设备到服务器的隧道。之后的应用内容保护取决于 HTTPS/TLS 等业务协议。实际速度取决于服务器、线路和设备；当前研究未进行吞吐或延迟测试。

11 / EXTENSION DIRECTIONS

在可用隧道之上，逐步扩展系统。

安装器提供部署与 peer 管理基础。下面是我们可以继续设计的方向，当前网页仅说明方案，尚未实现这些扩展。

扩展方向需要增加什么怎样判断有价值
分流与内网接入目标网段、路由与 DNS 策略、内网返回路径；站点互联需单独规划 peer 与路由。目标资源能访问，其他流量按预期走本地；检查网段冲突、IPv6 和重启恢复。
按设备限制访问以已认证 peer 的内部 IP 为基础，补充防火墙、资源范围和设备隔离。既验证允许的访问，也验证被禁止的访问；AllowedIPs 绑定本身不等于完整 ACL。
配置分发与生命周期设备登记、受控配置交付、密钥替换、丢失设备撤销、配置版本与管理员权限。能单独授权和撤销，重启后保持状态；减少误发凭据、共用密钥与配置漂移。
Web 管理与 API在安装管理能力外增加鉴权、授权、操作校验、审计与有限管理接口。管理操作可追溯，权限范围明确；避免把任意系统命令执行包装成开放 API。
观测与容量管理收集握手、endpoint、收发量、资源消耗和业务探测；制定告警与容量基线。区分已配置、最近通信与业务可用；定位失败环节，并用实测决定扩容。
自动化与多网关配置模板、重复部署与备份恢复；规划备用节点、路由选择和切换策略。故障时业务能恢复；复制配置或添加第二台服务器不会自动形成高可用。
扩展顺序

先验证一台服务器、一台客户端的真实通信，再做需要的分流和访问限制；有设备规模与管理需求后，再投入分发、面板、监控和冗余。逐项定义验收结果，保留配置与实测记录。
